        Crash safety
        
Kill the tab mid-write

        
The button fires 60 inserts one after another (strict durability) and records every acknowledged id in sessionStorage the moment it is acknowledged. At a random point between acknowledgement 5 and 55 it starts the next insert and calls location.reload() immediately: no close(), no flush(), no waiting. When the page comes back it checks every acknowledged id.

        Kiosks · edge · no backend
        
Corrupt a file, still open

        
The store keeps two snapshot slots and writes each checkpoint into the one that does not hold the newest snapshot, so a tab killed mid-checkpoint can only tear that slot. These buttons damage the real files in OPFS (through a throwaway worker holding a sync access handle) and then reopen.

        

          
          
          
          
        

        
Crash mid-checkpoint writes a checkpoint, saves 3 notes into the log, reloads without closing, and, before the store reopens, writes half of a newer checkpoint over the slot the next checkpoint targets: exactly what a tab kill mid-checkpoint leaves. Tear the newest and Tear both damage data that has no intact copy left; the page shows how open refuses instead of guessing.

        Agent memory
        
Wrong model, refused

        
Vectors from two embedding models are not comparable; mixing them returns confident nonsense. The store records its embedding space in every snapshot, so opening it with a different model is refused before that model is downloaded.
